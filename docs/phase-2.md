# Phase 2 — Database Layer

## Scope

Add the PostgreSQL persistence layer on top of the Phase 1 scaffold:

- SQLAlchemy 2.0 declarative models (typed `Mapped[...]` columns) for: `users`, `workspaces`,
  `workspace_members`, `patients`, `leads`, `calls`, `call_transcripts`, `call_summaries`,
  `appointments`, `providers`, `services`, `business_hours`, `ai_agents`, `integrations`,
  `notifications`, `audit_logs`.
- Alembic migration environment (`backend/alembic/`) wired to the app's `Settings` so the DB URL
  comes from `.env` / environment variables, never hardcoded in `alembic.ini`.
- Initial migration (`87c588deaec8_initial_schema.py`) creating all 16 tables.
- `app/database/session.py`: SQLAlchemy engine, `SessionLocal`, and a `get_db()` FastAPI
  dependency for request-scoped sessions.

## Design notes

- **UUID primary keys** everywhere (`UUIDPKMixin`), generated client-side via `uuid.uuid4`.
- **Multi-tenancy**: every tenant-owned table gets an indexed, non-nullable `workspace_id` FK via
  `WorkspaceOwnedMixin` (`ON DELETE CASCADE`). `users` is a global identity table — access to a
  workspace is granted through `workspace_members`, which is itself tenant-owned.
- **Timestamps**: `created_at` / `updated_at` on every table via `TimestampMixin`, except
  `audit_logs`, which is append-only and has `created_at` only (no `updated_at` — audit rows
  are never edited after creation) and a nullable `workspace_id` (some audited actions are
  platform-level, not scoped to one workspace).
- **Foreign keys** use `ON DELETE CASCADE` for strictly-owned children (e.g. `workspace_members`,
  `call_transcripts`) and `ON DELETE SET NULL` for optional/soft references (e.g.
  `calls.patient_id`, `appointments.provider_id`) so losing a provider doesn't delete history.
  `appointments.patient_id` is `CASCADE` since an appointment can't exist without its patient.
  `call_summaries.call_id` is unique (one summary per call).
- **JSON config** (`ai_agents.config`, `integrations.config`, `audit_logs.extra_data`,
  `call_summaries.action_items`) uses PostgreSQL `JSONB`. `integrations.config` is documented as
  non-sensitive settings only — secrets belong in a secrets manager, not this table.
- **Indexes**: every FK column, plus commonly-filtered columns (`status`, `email`, `phone`,
  `start_time`, etc).

## Credentials

No database credentials are committed. `.env.example` documents the required variables
(`DATABASE_URL` or the discrete `POSTGRES_*` fields); the local, gitignored `.env` holds
whatever values a developer's own Postgres instance needs.

## Testing without a live PostgreSQL instance

This environment had no local PostgreSQL server or Docker available, so the migration and
models were verified without executing DDL against a real database:

- `python -c "from app.models import Base; ..."` confirms all 16 tables register on
  `Base.metadata` with no import errors.
- The initial migration was **autogenerated** against a throwaway SQLite file (via the
  `ALEMBIC_DATABASE_URL` override in `alembic/env.py`) purely to drive Alembic's diff engine;
  the column *types* in the generated migration (`UUID`, `JSONB`) come from the model metadata
  itself, not from the SQLite connection, so the migration is genuinely Postgres-shaped.
  Attempting to actually run that migration against SQLite correctly fails (SQLite can't render
  `JSONB`), which confirms the migration isn't secretly SQLite-flavored.
- `alembic upgrade head --sql` was run in **offline mode** against a `postgresql+psycopg2://`
  URL, which renders the full DDL for the PostgreSQL dialect without needing a live connection —
  this is the actual verification that the migration is valid PostgreSQL. It exited 0 and
  produced correct `CREATE TABLE` / `CREATE INDEX` / `ALTER TABLE ... FOREIGN KEY` statements in
  dependency order.
- `backend/tests/test_database.py` structurally checks the models via SQLAlchemy's `Table`
  objects (PK/FK/index/unique/nullable shape, timestamp columns) and checks `Settings`' URL
  assembly — all without opening a connection.
- One real bug was caught and fixed this way: Alembic's autogenerate emitted
  `postgresql.JSONB(astext_type=Text())` without importing `Text`, which would have raised
  `NameError` the first time the migration ran. Fixed to `sa.Text()`.

**Not yet verified**: actually running `alembic upgrade head` against a live PostgreSQL server,
and round-tripping real rows through the ORM (insert/query/relationship loading). Do this before
relying on the migration in a real environment:

```bash
alembic upgrade head
python -c "from app.database.session import SessionLocal; from app.models import Workspace; db = SessionLocal(); db.add(Workspace(name='Test', slug='test')); db.commit()"
```

## Out of scope (unchanged)

Authentication, AI engine, telephony integration, appointment-booking business logic,
notification delivery — schema exists for these where relevant, but no behavior is implemented.
